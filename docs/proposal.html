Critique

Review marks for Obsidian built on CriticMarkup: one-gesture authoring from a selection, consistent rendering in Live Preview, Source and Reading modes, comment indicators in the right margin, and a review panel where every mark can be acted on.

Goals and principles

The plugin exists to make reviewing a note feel like reviewing in a word processor, without leaving plain Markdown. Four principles drive every decision below.

  • The file is the only state. Every mark, comment, author and timestamp lives in the note as CriticMarkup. Git, Sync, other plugins and AI agents all see the same thing. Nothing is stored in plugin data except preferences.
  • Authoring is a gesture, not typing. Select text, pick a mark type, optionally type a comment. The raw syntax is never required, in any mode.
  • Every mode renders the same mark the same way. Live Preview and Reading hide the syntax. Source mode shows it, dimmed, with the content styled identically.
  • Comments are visible where they belong. A thread shows as an indicator in the right margin at its line, as a popover on click or hover, and as a card in the review panel. The three views stay in sync.

Non-goals for the first release: real-time collaboration, a comments database, any network access.

Takeaways

  • Track Changes has the cleanest data model: a parser that skips code blocks, anchored edits that are re-validated against the live document before writing, and a metadata prefix that is stripped for free on accept. Critique adopts its syntax so the two plugins, and the agent skill written for it, interoperate.
  • Review Comments has the authoring gesture you want: a floating bar that appears on selection. It is comment-only, and its pipe-delimited metadata lives inside the comment body, which cannot extend to additions or deletions without leaking into accepted text.
  • Commentator is the most ambitious (suggestion mode, vault index, annotation gutter) and shows how a right-side gutter can be built as a CodeMirror extension. Its metadata is JSON inside the mark, which other tools do not read, and its own README warns about data loss in suggestion mode.
  • Review Critic documents its track-changes editing rules well, including the structural-markdown bypasses. It is a good reference if suggestion mode is built later.
About the missing Track Changes panel
Track Changes 2.3.0 declares minAppVersion 1.13.0 and uses the new settings-definition API from that release. On an older Obsidian build the plugin can load partially and the view never registers. Checking Settings → About for the app version and the developer console for a load error would confirm it. Either way, Critique will target a lower minimum (1.8) and avoid APIs newer than that.

Syntax

Critique reads and writes standard CriticMarkup. The five marks are unchanged. Metadata is an optional attribute prefix placed between the opening brace and the sigil, identical to the Track Changes format, so a note annotated by either plugin or by an agent renders in both.

Addition{++after the retry fix,++}
Deletion{--mostly--}
Substitution{~~March 3~>March 10~~}
Highlight{==Owner: platform team==}
Comment{>>Do we have a dashboard link for this?<<}
With metadata{author="Chris" date="2026-10-28T14:05-07:00"~~March 3~>March 10~~}
Anchored comment{==Latency improved by roughly 40%.==}{author="Chris" date="…">>Do we have a dashboard link?<<}
Thread{==span==}{author="Chris" date="…">>root<<}{author="Dana" date="…">>reply<<}
Comment on a change{author="Chris"--rewrite the queue--}{author="Chris">>Keep this as a substitution instead?<<}
Resolved thread{author="Chris" date="…" status="resolved">>Title case here?<<}

Rules

  • Attributes are key="value" pairs, space separated, no whitespace after the brace. A value may not contain ", braces or a newline. A prefix that fails to parse makes the mark fail locally instead of swallowing text, which is the corruption defence Track Changes relies on.
  • Recognised keys: author, date (ISO 8601, precision configurable, display-only), status (resolved), and optionally label (see extras). Unknown keys are preserved untouched.
  • Threads are adjacent comment marks with no gap between them. The first is the root. Nothing else is needed to link replies, so there are no ids to generate or keep unique.
  • Anchors: a highlight, addition, deletion or substitution directly before a thread is its anchor. The panel shows one card for the pair. Accepting or rejecting a change deletes its attached rationale thread; deleting a thread never deletes its anchored change.
  • Comments stay on one line. A hard line break typed into a comment is stored as the two characters \n and rendered back as a break, so a comment never splits a paragraph.
  • Code is left alone. Marks inside fenced, indented or inline code are not parsed, in any mode.
  • Accept keeps additions and new text, drops deletions, old text, comments and highlights, and strips every prefix. Reject is the mirror. Both produce plain Markdown with no trace of the mark.

Authoring from a selection

Selecting text in any mode shows a small toolbar above the selection. One click wraps the selection. Comment, Substitution and Highlight open a second step where the comment or replacement is typed; Addition and Deletion apply immediately. Every mark written by the plugin is stamped with the configured signature and timestamp.

Other ways in

  • Right-click menu. A Critique section in the editor context menu with the five mark types, and, when the cursor is inside a mark, Accept, Reject, Comment on this change, Edit metadata. Reading mode gets the same menu via its own context-menu handler.
  • Command palette. One command per mark type plus Accept at cursor, Reject at cursor, Next mark, Previous mark, Toggle panel, Toggle preview mode, Finalize. All bindable to hotkeys. Suggested defaults: ⌘⇧+ add, ⌘⇧- delete, ⌘⇧M comment.
  • No selection. Comment inserts a standalone comment at the cursor. Addition inserts an empty {++|++} with the cursor inside. The other three do nothing and say so in a notice.
  • Selection inside an existing mark. The toolbar switches to the mark’s actions (Accept, Reject, Comment, Remove) rather than offering to nest a mark. Nested marks are never written.

Reading mode

Reading mode has no editor, so the selection is a DOM range. Critique maps it back to source offsets: the block containing the selection reports its source line range through Obsidian’s section info, the rendered text of the block is aligned to the block’s source text with a character diff, and the selection’s start and end are carried across the equal runs of that alignment. The mark is then written to the file with the same anchored-edit path as the editor, and Reading mode re-renders. When the alignment is ambiguous (the selected text appears twice in a block and the alignment cannot separate them) the plugin falls back to opening the note in Live Preview with the selection restored, and says why. This is the one feature none of the existing plugins attempt, and it is the main technical risk in the plan.

Rendering in each mode

Marks are styled the same in all three modes. Live Preview and Reading hide the syntax. Source mode keeps the full syntax visible but dims the delimiters and metadata so the content stays readable.

Text decoration is a setting per type. Deletion defaults to strikethrough plus color; addition to color plus underline so the two remain distinguishable for color-blind readers. A “color only” and a “bold” option exist for each. Every color is a CSS variable, so theme snippets can override them too.

On top of the per-type decoration, a global Mark style setting controls how marked spans are called out in the text:

  • Highlighted (default): the span gets a faint background tint in the mark’s color, plus the per-type decoration.
  • Dashed underline: no tint; a dashed underline in the mark’s color, plus the per-type decoration. Quieter for long reads and for themes where tints clash.
  • Off (tray only): no inline styling at all. The margin tray alone shows where marks are, and hovering an indicator briefly outlines its span. In this style the margin indicators are forced on and cover every mark type, not only comments.

The setting applies to Live Preview, Source and Reading mode alike. In Source mode the delimiters stay dimmed in every style so the syntax remains readable.

Margin indicators and popovers

An indicator appears in the right margin for every line that holds at least one thread. It shows the message count, takes the comment color, and turns solid when its thread is focused in the popover or panel. Lines with marks but no comments get no indicator, so the margin only ever says “there is something to read here”.

  • In the editor (Live Preview and Source) the indicator layer is a CodeMirror view plugin that positions one element per thread at the line’s vertical coordinate, re-measured on every viewport change, so it survives folding, wrapped lines and embeds. This is simpler and less fragile than a custom gutter and works identically in both editor modes.
  • In Reading mode the post-processor adds the same layer to each rendered section. Positions are measured from the anchor element’s bounding box, so an indicator sits beside the exact wrapped line of its anchor.
  • Several threads on one line stack into one indicator with a total count; clicking it lists the threads.
  • Click opens the thread popover shown above. Hover over any mark (not just comments) shows a lighter card with the type, author, time and quick Accept / Reject, so a reviewer can process simple changes without opening the panel.
  • Panel sync. Clicking an indicator also scrolls the panel to the matching card; clicking a card scrolls the editor to the mark and pulses its indicator.

Review panel

The panel is a standard Obsidian view in the right sidebar (or a split, by setting), toggled with a ribbon icon, a command, or by clicking any indicator. It lists every mark in the active note in document order as a card. Cards are live: edits in the note update them, and actions on a card write to the note through the same anchored-edit path as everything else.

Card behaviour

  • Every card shows the type, author, relative time (absolute on hover) and a jump target. Clicking the card body scrolls the note to the mark and flashes it. The card that holds the cursor’s mark is outlined.
  • Change cards (add, delete, replace) show the diff, with changed characters emphasised inside a substitution, plus Accept, Reject and Comment. A rationale thread attached to the change is rendered inside the card and goes away with the change.
  • Thread cards quote the anchored span and list messages. Each message can be edited in place (double-click or the pencil in its menu), with ⌘↩ to save and Esc to cancel. Author and date on an edited message are kept; an edited="…" timestamp is optional (setting). Reply appends a message with the current signature. Resolve sets status="resolved" on the root; Reopen clears it. Delete removes one message or the whole thread, with confirmation by default. Deleting a thread removes its highlight anchor; it never removes a change anchor.
  • Highlight cards offer Comment (starts a thread on the highlight) and Remove highlight.
  • Header shows counts, filters (All, Changes, Comments, Mine, author names when more than one), a resolved toggle, sort (document order or newest first), and a menu with Accept all, Reject all, Finalize and Collapse all.
  • Safety. If the note changed between drawing a card and clicking it, the action re-finds the mark by its anchoring text before writing; if it cannot be found exactly once, the action is refused with a notice instead of editing the wrong range.

Review actions

  • Accept / Reject at cursor, for a selection, for the whole note, or per card. Multi-cursor selections are handled as one transaction. Everything goes through the editor’s undo stack when the note is open.
  • Navigation. Next mark / Previous mark commands cycle through marks in the note; the panel and indicators follow.
  • Preview modes. A view-header toggle switches the note between Markup (default), Accepted (how the note reads if every change is accepted; comments and highlights hidden) and Original (every change rejected). Both previews are display-only and never touch the file. The active mode is per note view and shown in the status bar.
  • Finalize. A dialog that accepts or rejects all changes, removes comments and highlights, and strips metadata, with each step as a checkbox. Produces a clean note ready to publish. Defaults are configurable.
  • Export strict CriticMarkup. Copies or writes a version of the note with metadata prefixes removed, for tools that implement only the base syntax (Marked, MultiMarkdown, pandoc filters).
  • Status bar. “4 changes · 2 threads” for the active note; click toggles the panel.

Settings

Everything visual and everything written into the file is configurable. The signature and timestamp options determine the metadata prefix; the appearance options map to CSS variables so theme snippets can override them too.

Proposed extras

Beyond the list you gave, these fill gaps I hit in the existing plugins or that fall out naturally from the design. Each is small except the last two.

Resolve and reopen threads phase 2

A status="resolved" attribute on the root comment. Resolved threads dim in the note, collapse in the panel and drop out of the indicator count. Nothing is deleted, so the discussion stays in the file for anyone who wants it.

Author colors and “Mine” filter phase 2

Each author name maps to a stable hue for anchors, avatars and the panel filter. Makes a note reviewed by two people, or by you and an agent, readable at a glance.

Accepted / Original preview phase 2

Read the note as it would be if everything were accepted or rejected, without touching the file. Useful before deciding, and for printing or exporting to PDF.

Copy without markup phase 1

Optional clipboard transform so a paragraph copied out of a reviewed note comes out as accepted text.

Comment labels optional

An optional label="question" attribute with a configurable set (question, edit, praise, note), shown as a small tag on the chip and card. Borrowed from Review Comments. Easy to add, easy to leave out; see the decisions below.

Agent interoperability phase 2

Because the syntax matches Track Changes, its reviewer skill and the Claude Code plugin written for it already produce marks Critique renders. Critique ships its own short SKILL.md so an agent can review a note and reply in threads.

Vault-wide review view phase 3

A second view listing open threads and pending changes across the vault, grouped by note, built from the metadata cache. Helps when review spans several notes.

Suggestion mode phase 3

A toggle that turns ordinary typing into additions and deletions, as Commentator and Review Critic do. Valuable but the riskiest feature in this space; it is scoped last and gated behind the structural-safety rules Review Critic documents.

Architecture

One parser feeds every surface. All writes go through one operations layer that anchors each edit to the text around it and re-validates before dispatching, so stale panel state can never corrupt the note.

Known hard parts

  • Obsidian’s own parser sees the inner syntax. {~~old~>new~~} contains ~~…~~, which Obsidian renders as strikethrough, and {==…==} contains a native highlight. In the editor the plugin’s decorations take precedence; in Reading mode the post-processor receives already-rendered <del> and <mark> elements and must re-find the mark across them. Track Changes and Review Critic both solve this and the approach is well understood.
  • Reading-mode selection mapping, described under Authoring. The fallback to Live Preview keeps the feature usable even where alignment fails.
  • Marks spanning block boundaries (a deletion covering two paragraphs) are legal CriticMarkup but break per-line rendering. The toolbar will split such a selection into one mark per paragraph, as word processors do.
  • Mobile. The selection toolbar becomes a bottom sheet and the panel is a full-height drawer. Hover cards are replaced by tap-to-open. No desktop-only APIs are used.

Stack: TypeScript, esbuild, the CodeMirror 6 packages Obsidian exposes, no runtime dependencies. Unit tests for the parser and operations run under Node without Obsidian; rendering is checked in a test vault.

Decisions to make before building

Settled 2026-10-28. All recommendations below were accepted. Comment labels (question 4) are included as an optional attribute, off by default. One addition: a global Mark style setting with Highlighted, Dashed underline, and Off (tray only), described under Rendering and Settings.
1. Metadata syntax Attribute prefix ({author="…" date="…"++text++}) or strict CriticMarkup with metadata carried in an adjacent comment? Recommended: the attribute prefix. It is stripped on accept, is already produced by Track Changes and its agent tooling, and the strict export command covers external tools.
2. Multi-line comments Store hard line breaks as a literal \n (keeps each comment on one line, matches Review Comments) or allow real newlines inside a comment? Recommended: the escape. It keeps paragraphs intact and makes threads unambiguous.
3. Timestamp format ISO 8601 with local offset at minute precision (2026-10-28T14:05-07:00), or UTC with seconds? Recommended: local offset, minutes. Readable in Source mode, sorts correctly, and the precision is a setting anyway.
4. Comment labels Include the optional label attribute and type picker in the comment popover, or keep comments untyped? No recommendation; it depends on whether you use question/edit/praise distinctions when reviewing.
5. Suggestion mode Keep it in phase 3 as proposed, or drop it from scope entirely? Recommended: keep it in phase 3 and decide after phases 1 and 2 are in daily use.
6. Name and id “Critique”, plugin id critique, CSS prefix cq-. The id needs to be unique in the community list; “critique” is currently unused there.
